## Knowledge / Wiki Business Logic

| Concept | Current behavior | User-facing interaction | Runtime usage |
| --- | --- | --- | --- |
| Knowledge Base | A workspace-level container for source materials, generated pages, processing config, graph view and retrieval index. | Users create/manage KBs in Wiki, upload raw materials, process them into pages, edit pages and inspect graph/config. | KBs are not automatically injected into chat unless an Agent explicitly binds them. |
| Wiki Page | A structured page inside one KB, generated from raw materials or created as a template/default page. | Users read/search/edit pages from the currently selected KB page list; archived pages remain under that KB's archived section instead of mixing with the KB list. System/locked pages remain protected by existing page guards. | Chat uses page summaries/snippets first; full page reads are available through wiki tools when relevant. |
| Agent KB binding | Optional list of KB ids stored on the Agent. Empty list means no persistent wiki context is injected. | Users bind/unbind KBs in Agent create/edit under "会话知识库". | `WikiContextService` and `ContextRouterService` only use KBs explicitly selected on the Agent. |
| Template default KB seed | Built-in templates can create starter KBs/pages as sample/default data. This is not a mandatory binding. | Template cards show default KB seed readiness only when the template declares seed data. | Seeded KBs become normal workspace KBs; users decide whether to bind them to an Agent. |
| System Wiki page | Scaffold/operational page created by the platform (for example overview/log) with protected page guards. | These pages stay inside the KB but are not treated as ordinary business seed content and remain protected from normal delete flows. | Wiki guards/tools can read them when needed, but ordinary business statistics and delete operations should continue to respect the protected page type. |
| Template seed Wiki page | Starter page materialized from a built-in template, typically to provide default rules/examples for a business Agent. | Users see and edit these pages like normal KB content after creation. | They count as normal business knowledge content once seeded, even though the initial source is a template declaration. |

### Local Agent implementation guardrails

- Never bridge full local directory contents to remote reasoning by default.
- Prefer `list/search/index/snippet` over recursive full-file reads.
- Keep local execution authority in Desktop/App; keep audit/policy/run-state authority in Server/Harness.
- Reuse Phase 4 workspace policy and Phase 5 project cache/router instead of introducing a disconnected local-agent stack.
- Treat skills/MCP as optional capability extensions, not as the primary substrate for core local coding workflows.

## Status Update Rules

- Before starting a phase, set its status to `in_progress` and record expected modules.
- After completing a phase, set its status to `done`, list actual modified files, record tests, and capture residual risks.
- If blocked, set status to `blocked` with reason and recommended path.
- Before moving to the next phase, check `git status` and confirm unrelated files were not changed.
